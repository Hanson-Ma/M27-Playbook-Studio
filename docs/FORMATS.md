# Data contract: web editor ⇄ game tools

The web editor (`app/`) only reads and writes files in this repo. Everything that touches Madden 27 runs on the game PC
through `tools/export.ps1`. If the editor writes these files correctly, the game side builds them.

```
                 (any machine)                          │             (game PC)
 data/library/*.json  ──read──▶  app/  ──write──▶  playbooks/*.json        ──▶ tools/export.ps1 ──▶ build/PBOOKOFF-<NAME>  → Documents\Madden NFL 27\saves
 (game play library,                                playbooks/plays/*.json  ──▶                  ──▶ mods/pbstudio.fbmod   → MMC Mod Manager
  regenerated by PlayDump library)                  app-data/*.json (editor-only: concepts, tags, notes)
```

## Coordinates and units (shared by everything)
- Field coordinates are in **yards relative to the ball**. `x` is lateral, with **+x toward the offense's right**. `y` is depth, with **-y into the offensive backfield** (the LOS is y=0). QB under center is about (0,-1.4); a shotgun QB is about (0,-6).
- Angles are in **degrees**: 0 = toward +x (right), 90 = straight upfield, 180 = toward -x (left), 270 = straight back.
- `distance` is in yards; `speed` is 0–100.
- **Player slots**: a play's `assignments[i]` belongs to the player in slot `i` of its set's `movements.Normal[i]`. The order is fixed by the set, usually 0 QB, 1 HB/RB, 2–5 skill players, 6–10 LT LG C RG RT. Always look up by index; don't assume positions.
- **Read progression** (`reads[].pos`) refers to a slot number (1–5 are the eligible non-QB skill slots).

## 1. `data/library/` — read-only game data (export with `PlayDump library data/library`)
| file | shape |
|---|---|
| `formations.json` | `[{formId, name, type, asset}]` |
| `sets.json` | `[{setId, name, asset, formation (asset), classification, setType, canFlip, movements: {Normal: [Position], M1left: [...], ...}}]`, where `Position = {pos, depth, x, y, facing, stance, group, motionMan}`. `Normal` is the base alignment; other keys are motion presets. |
| `plays.json` | `[{playId, name, asset, set (asset), offensePlayType, defensePlayType, blocking (asset), runHole, vip, allowHotRoutes, canFlip, assignments: [assignmentAsset per slot], reads: [{pos, pct, concept, combo}]}]` |
| `assignments.json` | `{ "<asset>": {id, routeType, steps: [Step]} }`, where `Step = {type, ...fields}` |

Names repeat across folders (several sets are called "Normal", and a minigame formation is also called "Shotgun"). **Identify things by `asset` or by id, never by display name alone.**

### Step types you'll see (assignment chain vocabulary)
Each player runs their steps in order. Every chain ends with `None`.
| type | fields | meaning |
|---|---|---|
| `RunRoute` | distance, direction, speed | run a route leg (pass routes) |
| `MoveDirection` | distance, direction, speed | move (non-route movement, screens, leads) |
| `ReceiveHandoff` | distance, direction, speed | path while taking a handoff |
| `ReceiverCut` | direction (`RECEIVER_CUT_DIR_LEFT/RIGHT`), cutType (`RECEIVER_CUT_ANGLE_45/67/90/22/CURL/POSTCORNER/180_PARTIAL/BUBBLE_SCREEN/...`) | a cut animation between legs |
| `GetOpen` | — | find space at the route's end |
| `Delay` | time | wait (seconds) |
| `PassBlock` | time, flags | pass protect (`ProtectReceiver` = screen blocking) |
| `RunBlock` | stalkDistance, slamDuration, time, flags, receiverBlockType | run block (scheme decides the target) |
| `LeadBlock` | blockingTechnique (`KICKOUT/TRAP/LEAD_THROUGH_HOLE/STALK_BLOCK/CRACK_BLOCK/...`), blockingGap (`A_GAP_RIGHT ... RUN_HOLE`) | lead, kickout, pull or stalk block |
| `InitialAnim` | anim (`MOVETYPE_COUNTER_PULL/POWER_PULL/SKIP_PULL/TRAP_PULL/SCREEN_PULL/WRSTART/BACKSTEP/HOPSTEP/...`), direction | opening step (pulls start here) |
| `QBScramble` | dropBackType (`DROP_TYPEENUM_QBDROP_*`), direction, distance | QB drop or rollout |
| `CannedHandoff` | playerNum, handoffAnim, flippedHandoffAnim | QB/RB handoff animation pair — must match between QB and ballcarrier |
| `HandOffTurn` / `HandOffGive` / `HandoffFake` / `OptionHandoff` | … | handoff / fake / read mechanics |
| `AutoMotion` | waypoints [{position {x,y}, speed, facingAngle, …}], startEvent (`AUTOMOTIONSTARTEVENT_SNAP`…) | scripted motion. Waypoint positions are **absolute** field coords. |
| `OverrideFormPos` | stance, offsetX, offsetY | play-specific realignment |
| `ManCoverage`, `HookZone`, `DeepZone`, `FlatZone`, `CurlFlatZone`, `PassRush`, … | … | defense |

**Play art is generated by the game from these steps.** To draw a route: start at the player's alignment, then add each `RunRoute`/`MoveDirection`/`ReceiveHandoff` leg as a vector (`distance` at `direction`). `ReceiverCut` is a corner marker; `GetOpen` and `Delay` end or pause the path.

## 2. `playbooks/<name>.json` — a custom playbook (becomes a save file)
```jsonc
{
  "name": "STUDIO",               // save file becomes PBOOKOFF-STUDIO (PBOOKDEF- for defense); A–Z0–9 only
  "side": "offense",
  "notes": "free text",
  "formations": [
    { "formation": "Shotgun", "sets": [
      { "set": "Y Trips Wk", "plays": [
        { "play": "PBS GT Counter", "audible": 2, "cpu": { "FirstDown": 40, "3rdAndShort": 30 } },
        { "play": "Inside Zone" }
      ]}
    ]},
    { "formation": "Special", "sets": "template" }   // copy this formation's sets/plays from the template save
  ]
}
```
- `formation` and `set` are display names. The set is resolved inside the formation's folder; `play` is resolved inside that set. A play can be any library play or any custom play from `playbooks/plays/`.
- `audible`: 1–4, at most one play per slot in a set. (The game stores slots 1/2/3/4 as Flag bits 2/4/16/8; the builder handles that.)
- `cpu`: CPU play-call weights by situation (0–100). Allowed keys: `FieldGoal 3rdAndShort StopClock GoalLine RedZone Insidefive 2ndAndLong 3rdAndMedium 3rdAndLong Punt ConserveTime FakePunt FakeFieldGoal WasteTime Kneel Kickoff KickoffOnside 2ndAndMedium KickoffSafety PuntMaxProtect 2ndAndShort Hailmary GoalLinePass SignaturePlays ConserveTimeSafe RedZoneFringe RedZone_16_to_20 RedZone_11_to_15 RedZone_6_to_10 StopClockUser StopClockFakeUser 4thAndShort 4thAndMedium 4thAndLong GoFor2 FirstDown Squib Playaction GoFor1 RedZone_3_to_5 3RDExtraLong 4THExtraLong SuddenChange LastPlay`.
- **Keep special teams.** Include `Special`, `Kickoff` and `Safety Kickoff` (and usually `Goal Line Offense`), as `"template"` or explicitly.
- Capacity limits per save: **750 plays, 40 formations, 75 sets, 2200 CPU-weight rows**.
- Play order in the file is saved, but the in-game list may re-sort (the Formation tab sorts by usage). Treat the order as a preference.

## 3. `playbooks/plays/*.json` — custom plays (become `mods/pbstudio.fbmod`)
All files in this folder are merged into **one** mod, because every play mod edits the shared GlobalPlaySheet.
```jsonc
{ "plays": [
  {
    "name": "PBS Snag",                     // in-game name; unique
    "asset": "PBS_Snag",                    // asset leaf name; unique within the set folder, [A-Za-z0-9_]
    "base": "<asset of an existing play IN THE SAME SET>",   // supplies alignment, handoff/protection mechanics, flags
    "playType": "OffensePlayType_PassShotgun",               // optional; defaults to base's
    "blocking": "BTCounter",                 // optional blocking scheme asset leaf (run plays)
    "runHole": 4,                            // optional
    "players": {                             // only slots you change; others keep the base play's assignment
      "3": "RunRoute/WR_Run90for30",         // reuse an existing assignment (path under .../Assignments/)
      "2": { "new": "PBS_Slot_Corner7",      // author a new assignment (asset leaf under Assignments/PBS/; reused if the name repeats)
             "routeType": "AssignRouteType_RR_Corner_Middle",
             "template": "RunRoute/...",     // optional source to copy; default = the base play's assignment for this slot
             "keep": 0,                      // keep the first N steps of the template (e.g. 1 = keep an AutoMotion, 2 = keep a handoff precan)
             "steps": [ { "type": "RunRoute", "distance": 7, "direction": 90, "speed": 100 },
                        { "type": "ReceiverCut", "direction": "RECEIVER_CUT_DIR_RIGHT", "cutType": "RECEIVER_CUT_ANGLE_45" },
                        { "type": "RunRoute", "distance": 22, "direction": 45, "speed": 100 },
                        { "type": "GetOpen" } ] }   // trailing None is added automatically
    },
    "reads": [ { "pos": 5, "pct": 0.8 }, { "pos": 2, "pct": 0.7 } ]   // optional QB progression (concept defaults to Concept_Invalid)
  }
]}
```
Rules the editor must enforce:
- **The base play must come from the same set** as the new play. A play can't change its set, and handoff/pull mechanics depend on alignment.
- **Handoffs, fakes, options and pitches** (`CannedHandoff…`) must stay paired between the QB and the ballcarrier. Change them only by choosing a different base play, or with `keep` on both slots.
- Step `type` and enum values must exist. Take them from `assignments.json` (every value used anywhere in the game appears there).
- Editing an existing game play in place is not supported yet. Clone it as a new play instead.

## 4. `app-data/` — editor-only state (the game never sees it)
For example, `app-data/concepts.json` (user-defined pass/run concept categories and which plays carry which tags) and per-play notes.
The editor owns this format. Seed it from `plays.json` → `offensePlayType` and `reads[].concept`.
